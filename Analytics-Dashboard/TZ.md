## 1. Мета

Створити аналітичний вебдашборд, який показує зведену картину оперативної обстановки на карті України та в графіках. Обстановка складається з **чотирьох модулів**:

| Модуль | Що аналізується |
|---|---|
| **A. Повітряні удари і тривоги** | БпЛА, крилаті та балістичні ракети, КАБ; перехоплення, влучання, повітряні тривоги |
| **B. Артилерійські обстріли** | вогонь противника по позиціях і об'єктах та вогонь своїх засобів: системи, калібри, кількість пострілів |
| **C. Втрати особового складу** | лише агреговані показники за підрозділами та добами: загиблі, поранені, зниклі безвісти; причини втрат |
| **D. Документообіг ОКП** | вхідні документи на основний командний пункт: обсяг, категорії терміновості, час обробки, прострочення |

Дані зберігаються в PostgreSQL. Бекенд на FastAPI віддає їх через REST API. Фронтенд показує KPI, графіки та карту з умовними знаками (OpenStreetMap + milsymbol). Оформлення відповідає брендбуку ЗСУ, а знаки, час, таблиці та підписи відповідають Порядку.

Проєкт має **запускатися на будь-якому комп'ютері однією командою** (§4).

## 3. Принципи та обмеження

1. **Тільки синтетичні дані.** Усі записи генерує скрипт. Вони правдоподібні за структурою, але **не відображають реальних подій, втрат, документів чи координат**. Кожен запис має `is_synthetic = true`, а на кожній сторінці видно банер «Синтетичні дані. Навчальний проєкт».
2. **Умовні підрозділи.** Назви та номери своїх підрозділів вигадані й позначені як умовні, наприклад «1 омбр (умовна)». Реальні номери військових частин ЗСУ не використовуються. **Противник** (положення, назви) і лінія зіткнення беруться з відкритого джерела DeepStateMap і подаються з атрибуцією та датою «станом на».
3. **Без персональних даних.** Модуль C зберігає лише числа за підрозділом і добою: ні прізвищ, ні посад, ні інших ознак конкретних людей. Модуль D зберігає метадані документа (тип, терміновість, час), а не його текст.
4. **Гриф.** Позначки грифу в модулі D (наприклад, «ДСК») є лише синтетичною категорією для статистики. Сам дашборд позначається «По навчанню», за аналогією з п. 1.2.2 Порядку.
5. **Координати** подій генеруються як випадкові точки: удари — лише на вільній території; КАБ — у смузі 3–38 км від лінії зіткнення з нашого боку; вогневі позиції противника — лише на окупованій території. Прив'язки до реальних об'єктів немає.
6. **Брендбук** використовується як стилістична основа. Офіційні логотипи ЗСУ, видів і Сил не розміщуються (брендбук, с. 21).
7. **PostGIS не використовується.** Координати зберігаються в полях `lat`/`lon`, а просторові операції виконує генератор на Python.
8. Дашборд не є і не замінює офіційних систем.

## 4. Розгортання та перенесення на інший комп'ютер

### 4.1. Основний спосіб: Docker Compose (рекомендовано)

На іншому комп'ютері потрібен лише Docker Desktop. Версії PostgreSQL, Python і бібліотек зафіксовані.

| Сервіс | Образ | Призначення |
|---|---|---|
| `db` | `postgres:16-alpine` | Під час першого старту виконує `db/init/*.sql` через `/docker-entrypoint-initdb.d`. Дані зберігаються в іменованому томі. |
| `api` | `backend/Dockerfile` (`python:3.12-slim`) | FastAPI + роздача фронтенду. Стартує після healthcheck `db`. |

**Запуск:**
1. Встановити Docker Desktop.
2. `git clone …`, потім `cd Analytics-Dashboard`.
3. `docker compose up -d` і відкрити `http://localhost:8000`.

**Службові команди:**
- `docker compose down -v`: повне скидання.
- `docker compose exec db pg_dump …`: вивантаження дампу.

### 4.2. Запасний спосіб: без Docker

1. Встановити PostgreSQL 16 і Python 3.12.
2. `createdb dashboard`, потім `psql -d dashboard -f db/dashboard_dump.sql`.
3. `python -m venv .venv`, потім `pip install -r backend/requirements.txt`.
4. Скопіювати `.env.example` у `.env`.
5. `uvicorn backend.app.main:app --port 8000`.

### 4.3. Автономність

- Бібліотеки (Leaflet, markercluster, milsymbol, Chart.js) лежать локально в `frontend/vendor/` з фіксованими версіями.
- Шрифти лежать у `frontend/fonts/` (для офлайн-збірки вбудовуються в CSS), межі областей і зони DeepState — у `db/sources/` (для фронтенду збираються в `frontend/data/geo.js`).
- Інтернет потрібен лише для тайлів OpenStreetMap.
- Секрети зберігаються в `.env`, у git лише `.env.example`.

### 4.4. Офлайн-режим (відкрити `index.html` на будь-якому комп'ютері)

- Якщо сторінку відкрито як файл (`file://`) або API не відповідає за 2,5 с, дашборд завантажує знімок бази `frontend/data/dataset.js` і рахує всі показники в браузері (`js/offline.js` повторює SQL роутерів). Відповіді збігаються з API.
- Знімок формує `python -m backend.export_snapshot` або завантажується з `GET /api/snapshot.js` (з усіма внесеними записами). Розмір ≈ 6,4 МБ.
- Браузер не завантажує ES-модулі з `file://`, тому для офлайну потрібна збірка `tools/build.py` → `js/bundle.js` (класичний скрипт), шрифти вбудовуються в CSS, межі областей і зони — у `data/geo.js`.
- Записи, внесені офлайн, зберігаються в `localStorage` браузера і вивантажуються як `.sql` (INSERT-и для PostgreSQL) або `.json` (для імпорту в онлайн-режимі).
- Інтернет потрібен лише для тайлів OSM; без нього карта показує межі областей і знаки на сірому тлі.

## 5. База даних (PostgreSQL 16)

### 5.1. Довідники

```sql
CREATE TABLE oblasts (
  id SMALLSERIAL PRIMARY KEY,
  iso_code VARCHAR(6) NOT NULL UNIQUE,            -- 'UA-63'
  name_ua VARCHAR(64) NOT NULL, name_en VARCHAR(64) NOT NULL,
  center_lat NUMERIC(8,5) NOT NULL, center_lon NUMERIC(8,5) NOT NULL,
  is_frontline BOOLEAN NOT NULL DEFAULT FALSE,
  is_occupied  BOOLEAN NOT NULL DEFAULT FALSE
);

-- Умовні підрозділи (вигадані), спільні для модулів B, C, D і для шару «Свої війська» на карті
CREATE TABLE units (
  id SMALLSERIAL PRIMARY KEY,
  short_name VARCHAR(32) NOT NULL UNIQUE,         -- '1 омбр (умовна)'
  name_ua    VARCHAR(128) NOT NULL,
  echelon    VARCHAR(12) NOT NULL CHECK (echelon IN
             ('command','corps','brigade','regiment','battalion','company')),  -- табл. 8: ОСУВ «XXXX», ОТУ/корпус «XXX»
  branch     VARCHAR(16) NOT NULL CHECK (branch IN
             ('mech','tank','artillery','air_defense','airborne','support','hq','recon','marine')),
  parent_id  SMALLINT REFERENCES units(id),       -- поле M «вище формування»
  oblast_id  SMALLINT NOT NULL REFERENCES oblasts(id),
  lat NUMERIC(8,5) NOT NULL, lon NUMERIC(8,5) NOT NULL,
  sidc       VARCHAR(20) NOT NULL,                -- знак підрозділу (дружній), §8
  is_rear    BOOLEAN NOT NULL DEFAULT FALSE,
  is_command_post BOOLEAN NOT NULL DEFAULT FALSE, -- ОКП/КП, що приймає документи (модуль D)
  origin     VARCHAR(10) NOT NULL DEFAULT 'synthetic'  -- synthetic | manual | import
);

-- Підрозділи противника: відкриті дані DeepStateMap (db/sources/deepstate.json), 268 записів
CREATE TABLE enemy_units (
  id SMALLSERIAL PRIMARY KEY, name_ua VARCHAR(160) NOT NULL, label VARCHAR(24) NOT NULL,
  branch VARCHAR(16) NOT NULL,
  echelon VARCHAR(12) NOT NULL,                   -- army, corps, division, brigade, regiment, battalion, unknown
  sidc VARCHAR(20) NOT NULL, lat NUMERIC(8,5) NOT NULL, lon NUMERIC(8,5) NOT NULL,
  source VARCHAR(64) NOT NULL, as_of VARCHAR(32) NOT NULL
);

-- Засоби повітряного нападу (модуль A)
CREATE TABLE weapon_types (
  id SMALLSERIAL PRIMARY KEY,
  code VARCHAR(32) NOT NULL UNIQUE,
  name_ua VARCHAR(64) NOT NULL,
  category VARCHAR(24) NOT NULL CHECK (category IN
           ('uav','cruise_missile','ballistic_missile','guided_bomb')),
  sidc VARCHAR(20) NOT NULL,                      -- 'OHVPE----------' — «Вибух, підрив» (п. 6.12 Порядку)
  color_hex CHAR(7) NOT NULL,
  map_label VARCHAR(8) NOT NULL                   -- власний підпис на карті: БпЛА, КрР, БалР, КАБ (п. 2.2.16)
);

CREATE TABLE target_categories (
  id SMALLSERIAL PRIMARY KEY,
  code VARCHAR(32) NOT NULL UNIQUE,               -- energy, residential, transport, industry, military, other
  name_ua VARCHAR(64) NOT NULL
);

-- Джерела інформації: повний перелік скорочень п. 2.2.15 Порядку (27 кодів)
CREATE TABLE info_sources (
  code VARCHAR(8) PRIMARY KEY,                    -- 'АР'
  name_ua VARCHAR(80) NOT NULL                    -- 'артилерійська розвідка'
);

-- Умовні нормативи часу обробки документів ОКП (§6.3)
CREATE TABLE doc_sla_norms (
  urgency VARCHAR(12) PRIMARY KEY,                -- horizon, efir, buran, zlit, none
  name_ua VARCHAR(24) NOT NULL, norm_min INT NOT NULL, sort_order SMALLINT NOT NULL,
  is_conditional BOOLEAN NOT NULL DEFAULT TRUE
);
-- Лінія зіткнення за DeepState: межа окупованої території (сегменти);
-- e_lat/e_lon — точка лінії противника, зсунута на 2,5 км у його бік (для червоної лінії, п. 6.2.1)
CREATE TABLE contact_line (seq SMALLINT PRIMARY KEY, segment SMALLINT NOT NULL,
  lat NUMERIC(8,5) NOT NULL, lon NUMERIC(8,5) NOT NULL, e_lat NUMERIC(8,5) NOT NULL, e_lon NUMERIC(8,5) NOT NULL);
CREATE TABLE dataset_meta (key VARCHAR(32) PRIMARY KEY, value TEXT NOT NULL);
```

`is_rear` — тиловий підрозділ (втрати близькі до нуля). Усі таблиці фактів (§5.2–5.5) мають поле `origin` (`synthetic` / `manual` / `import`): так відрізняються записи, внесені через дашборд.

### 5.2. Модуль A: повітряні удари і тривоги

```sql
CREATE TABLE attack_waves (
  id SERIAL PRIMARY KEY,
  started_at TIMESTAMPTZ NOT NULL,
  ended_at   TIMESTAMPTZ NOT NULL CHECK (ended_at >= started_at),
  title VARCHAR(128)
);

CREATE TABLE strike_events (
  id BIGSERIAL PRIMARY KEY,
  occurred_at TIMESTAMPTZ NOT NULL,
  oblast_id SMALLINT NOT NULL REFERENCES oblasts(id),
  weapon_type_id SMALLINT NOT NULL REFERENCES weapon_types(id),
  wave_id INT REFERENCES attack_waves(id),
  target_category_id SMALLINT REFERENCES target_categories(id),
  launched    INT NOT NULL CHECK (launched > 0),
  intercepted INT NOT NULL DEFAULT 0 CHECK (intercepted >= 0),
  suppressed  INT NOT NULL DEFAULT 0 CHECK (suppressed  >= 0),   -- подавлено РЕБ
  hits        INT NOT NULL DEFAULT 0 CHECK (hits        >= 0),
  damage_level SMALLINT NOT NULL DEFAULT 0 CHECK (damage_level BETWEEN 0 AND 3),
  info_source VARCHAR(8) REFERENCES info_sources(code),
  reliability CHAR(2) CHECK (reliability ~ '^[A-F][1-6]$'),       -- поле J, табл. 13 Порядку
  lat NUMERIC(8,5) NOT NULL, lon NUMERIC(8,5) NOT NULL,
  is_synthetic BOOLEAN NOT NULL DEFAULT TRUE,
  CHECK (intercepted + suppressed + hits <= launched)
);

CREATE TABLE air_alerts (
  id BIGSERIAL PRIMARY KEY,
  oblast_id SMALLINT NOT NULL REFERENCES oblasts(id),
  alert_type VARCHAR(24) NOT NULL CHECK (alert_type IN
             ('air_raid','artillery_shelling','urban_fights','chemical','nuclear')),
  started_at TIMESTAMPTZ NOT NULL,
  ended_at   TIMESTAMPTZ CHECK (ended_at IS NULL OR ended_at > started_at),
  duration_min INT GENERATED ALWAYS AS (CASE WHEN ended_at IS NULL THEN NULL
               ELSE (EXTRACT(EPOCH FROM ended_at - started_at)/60)::INT END) STORED,
  is_synthetic BOOLEAN NOT NULL DEFAULT TRUE
);
```

### 5.3. Модуль B: артилерійські обстріли

```sql
CREATE TABLE artillery_fire (
  id BIGSERIAL PRIMARY KEY,
  occurred_at TIMESTAMPTZ NOT NULL,
  direction  VARCHAR(8) NOT NULL CHECK (direction IN ('incoming','outgoing')),  -- по нас / наш вогонь
```

### 6.3. Правила правдоподібності

**A. Повітряні удари і тривоги:**
- 60–70 % подій припадає на прифронтові області.
- БпЛА та ракети переважно вночі.
- Взимку більше ударів по енергетиці.
- 1–2 масовані атаки на тиждень.
- Перехоплення: БпЛА 75–92 %, крилаті ракети 65–85 %, балістичні 20–50 %, КАБ ≈ 0 %.

**B. Артилерія:**
- Лише прифронтова смуга до ~40 км від лінії зіткнення; вогневі позиції противника — тільки на окупованій території, цілі нашого вогню — там само.
- Співвідношення вхідного й вихідного вогню змінюється по тижнях.
- Пік припадає на світлий час доби.
- Калібр відповідає системі: міномет 82/120, гаубиця 122/152, РСЗВ 122/220/300.
- Розподіл класів калібру відповідає табл. 16 Порядку.

**C. Втрати:**
- Корелюють з інтенсивністю вхідного артилерійського й повітряного вогню по підрозділу з лагом 0–1 доба.
- Поранених приблизно у 3–4 рази більше, ніж загиблих.
- Зниклі безвісти рідкісні й з'являються сплесками під час «боїв».
- У тиловому підрозділі втрати близькі до нуля.

**D. Документи ОКП:**
- Надходження має добовий ритм: піки о 06.00–08.00 і 18.00–20.00 (донесення за станом).
- Частка терміновості: ГОРИЗОНТ ~2 %, ЕФІР ~8 %, БУРАН ~20 %, ЗЛІТ ~30 %, решта безкатегорійні.
- Час обробки залежить від терміновості. **Умовні нормативи** (`doc_sla_norms`, до підтвердження замовником):

  | Категорія | ГОРИЗОНТ | ЕФІР | БУРАН | ЗЛІТ | Безкатегорійний |
  |---|---|---|---|---|---|
  | Норматив | 10 хв | 30 хв | 60 хв | 3 год | 8 год |

  Типи документів (умовні): бойове донесення, бойове розпорядження, директива, попереднє розпорядження, запит, інформаційне повідомлення, розвідувальне зведення, заявка на МТЗ.
- Строк виконання `due_at = received_at + норматив`. Наприкінці періоду частина документів лишається в черзі (стан «Новий» / «В роботі»).
- 3–8 % документів прострочено; ≈ 6 % документів за останні 72 год «застрягли» в черзі.
- Кожен документ має отримувача: КП свого ОТУ (≈ 75 %) або ОКП ОСУВ.
- У дні масованих атак обсяг документів зростає.

**Загальні правила:**
- `info_source` і `reliability` розподіляються правдоподібно, переважно B2–C3.
- ≈ 5 % записів позначено як непідтверджені (`reliability` з цифрою 4–6). На карті й у таблицях вони показуються зі знаком «?» (п. 2.2.15 Порядку).

## 8. Умовні знаки за наказом № 140 і milsymbol

### 8.1. Висновок з аналізу документів

**Правило вибору знака (рішення замовника):** спершу шукати знак у Порядку (наказ № 140); лише якщо там немає — брати з APP-6 / MIL-STD-2525C. Власні позначення допускаються за п. 2.2.16 з поясненням у легенді.

Порядок (розділи 5–6) **запроваджує в ЗСУ знаки НАТО**. Він описує ту саму модульну систему, що й APP-6: обрамлення, заливка, позначка, модифікатори та ампліфікатори з тими самими літерами полів (A, B, C … AO). Тому:

- **milsymbol рендерить основу знака**: обрамлення, позначку, ешелон, модифікатори.
- Національні особливості Порядку реалізуються **налаштуваннями milsymbol і власним SVG-накладанням**. Окремий набір картинок не потрібен.
- Перемикач на карті тепер має режими **«Наказ № 140 (кольоровий)» / «Монохромний (друк)»**. Монохромний режим відповідає п. 2.2.13 Порядку та розділу 0202 APP-6: противник позначається подвійною лінією або підписом «ПТН».

### 8.2. Правила, взяті з Порядку

| Що | Правило | Джерело в Порядку | Реалізація |

| Належність | дружні: прямокутник/коло, ворожі: ромб, нейтральні: квадрат, невідомі: чотирилисник; повітряні: відкриті знизу, підводні: відкриті зверху | п. 5.2.4, табл. 4 | SIDC identity + dimension |

#### 10.2.1. Поведінка знаків від масштабу (вимога замовника)

Розмір знака залежить від масштабу карти (п. 5.4.3 Порядку): знаки збільшуються при наближенні, зменшуються при віддаленні й зникають, якщо віддалити далі від загального виду України. Крок зуму 0,5.

| Масштаб | Що видно |
|---|---|
| 5 | лише хороплет, зони і лінія; знаки приховано |
| 5,5 (уся Україна) | ОСУВ, ОТУ; армії й корпуси противника; потоки ОТУ → ОСУВ; удари й обстріли — кластери |
| 6,5 | + бригади; дивізії противника; потоки бригада → ОТУ |
| 7 | + полки |
| 8 | + батальйони; бригади й полки противника; потоки батальйон → бригада |
| 8,5 | + підписи знаків (T — номер, M — старший начальник) |
| 9 | + батальйони противника |
| 9,5 | + роти; потоки рота → батальйон |

Пороги для противника вищі, ніж для своїх: уздовж лінії зіткнення DeepState дає дуже щільне розміщення, і на масштабі 7 знаки противника закривали лінію (перевірено скріншотом). Набір шарів можна передати в URL: `?layers=units,docs,line`.
| 10 / 11 | місця уражень / обстріли без кластерів |

Розмір знака: 14 px на масштабі 5 → 42 px на 12 (лінійно). Реалізація: знак рендериться один раз, масштаб задає CSS-змінна `--s`, видимість — класи `mz-N` / `zl-N` на контейнері карти (без перемальовування SVG). Початковий вид можна передати в URL: `?z=9&c=48.75,37.4`.

#### 10.2.2. Потоки документів ОКП

Попередній варіант («зірка» з десятків ліній від кожного підрозділу до ОКП) був нечитабельним. Нове рішення:
- **агрегування по ланці управління:** документ іде від відправника вгору по `parent_id` до отримувача; ребро «підлеглий → старший» має вагу = кількість документів, що пройшли ним. Ребер стільки, скільки зв'язків в ієрархії (≈ 86), а не пар «відправник–ОКП»;
- **деталізація від масштабу** за тими самими порогами, що й знаки (§10.2.1): на загальному виді — лише 4 лінії ОТУ → ОСУВ;
- **товщина** ∝ √обсягу в межах своєї ланки; **колір** — частка прострочених: морська хвиля < 5 %, золото 5–10 %, червоний > 10 %; невелика стрілка — напрям; підпис біля ОКП/КП: «N док. · x %»; подробиці — у підказці.

**Взаємодія:**
- Кластеризація подій до масштабу 10 (удари) / 11 (обстріли); підрозділи не кластеризуються.
- Попап у форматі «поле: значення»:
  - час у форматі `ГГ.ХХ ДД.ММ.РРРР`;
  - джерело (скорочення з п. 2.2.15) і достовірність;
  - позначка «Синтетичні дані».
- Перемикач «Кольоровий / Монохромний».
- Легенда «УМОВНІ ПОЗНАЧЕННЯ».
- Клік на область фільтрує дашборд.

### 10.6. Чекліст оформлення графіків

Складено з Порядку та загальних правил візуалізації даних (джерела наприкінці). Кожен графік проходить чекліст перед прийманням.

**Заголовок і контекст**
- [ ] Назва відповідає на питання «що?» і без скорочень (п. 1.2.6 Порядку). Під нею підзаголовок: період, застосовані фільтри, одиниці виміру.
- [ ] Ключовий висновок, якщо він є, подано анотацією на графіку (наприклад, позначено масовану атаку), а не лише в тексті.

**Осі та числа**
- [ ] Кожна вісь має підпис з одиницею (`од.`, `пострілів`, `осіб`, `год`, `хв`, `%`). Підпис часової осі можна не ставити.
- [ ] Вісь Y стовпчикових графіків починається з нуля. Друга вісь Y не використовується: дві величини різного масштабу — дві панелі або точкова діаграма.
- [ ] Числа у форматі `uk-UA`: пробіл між тисячами, десяткова кома. Час у форматі `ГГ.ХХ ДД.ММ.РРРР`, київський (п. 2.1.1 Порядку).
- [ ] Шрифт осей і tooltip: body-стек, 12 px. Volja лише в назві (§9.2).

**Легенда і кольори**
- [ ] Легенда лише якщо рядів більше одного. Розміщена праворуч або знизу, не перекриває дані. Порядок у легенді збігається з порядком стеку. Коли можливо, ряди підписано безпосередньо.
- [ ] Не більше 5–6 кольорів, лише з палітри модуля (§9.1). Один зміст має один колір у всіх графіках.
- [ ] Червоний використовується лише для загрози, втрат і прострочення. Немає пар «червоний-зелений». Графік читається в градаціях сірого.
- [ ] Без 3D, тіней, градієнтів, кругових і кільцевих діаграм. Сітка світла, допоміжних ліній мінімум.

**Дані та достовірність**
- [ ] Під графіком зліва підпис джерела: «Джерело: синтетичні дані (генератор v…), станом на ГГ.ХХ ДД.ММ.РРРР». Для даних з полем `info_source` у tooltip показано скорочення за п. 2.2.15 Порядку (АР, РЛР, ПвР…).
- [ ] Відсутні значення не підміняються нулем: у tooltip і таблиці пишеться «немає відом.» (п. 2.3.6 Порядку), на лінії розрив.
- [ ] Неперевірені записи (достовірність *4–*6) позначені «?» (п. 2.2.15 Порядку) або винесені окремим рядом.
- [ ] Малі значення втрат (1–4) у зрізі «підрозділ × доба» показуються як «<5».

**Взаємодія і доступність**
- [ ] Tooltip показує точне значення з одиницею.
- [ ] Є експорт PNG і CSV.
- [ ] Для кожного графіка є `aria-label` і перемикач «Показати таблицю» з тими самими даними.
- [ ] Графіки перемальовуються після завантаження шрифтів і при зміні теми.

### 10.7. Внесення даних (вкладка)

- **Онлайн:** форма → `POST /api/entry/{kind}`; файл → перевірка `…/check` (таблиця помилок по рядках) → `POST /api/import/{kind}`. Після внесення кеш скидається, графіки і «станом на» оновлюються.
- **Офлайн:** ті самі перевірки в браузері (`js/entries-store.js`), записи в `localStorage`, одразу видно в графіках і на карті. Кнопки «Вивантажити .sql» і «Вивантажити .json».
- **Шаблони:** CSV (UTF-8 BOM, «;») і XLSX із заголовками-ключами та рядком-прикладом; Excel розбирається SheetJS у браузері.

## 13. Етапи та критерії приймання

| Етап | Результат | Критерій приймання |
